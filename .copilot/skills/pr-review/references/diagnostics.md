# Diagnostics

Diagnostics answer one question the posted review cannot: **is this process working?** Is the
second model earning its keep, which checks actually produce findings, and which model is
miscalibrated on severity.

Generated by `scripts/review_report.py`. Printed locally, never posted to the PR.

## Verbosity

| Level | Flag | Contents |
|---|---|---|
| `quiet` | — (skip the script) | Posted review only. |
| `normal` | `--verbosity normal` | Verdict, severity counts, unique finds per model, agreement rate, reviewer scoreboard. |
| `verbose` | `--verbosity verbose` *(default)* | Adds the findings matrix, check attribution, search-axis split, adversary outcomes, cleared-claim overturns, file coverage, wall clock. |
| `debug` | `--verbosity debug` | Adds the raw findings JSON. |

```bash
python3 scripts/review_report.py findings.json --verbosity verbose
python3 scripts/review_report.py --summary --last 20     # cross-run stats
```

## Metrics and how to read them

**Unique finds** — accepted findings only one reviewer produced. The headline. A second
model that never produces a unique find is not paying for itself; drop it or raise its
effort. On #4907, five of the nine accepted findings came from one model alone and three
from the other — near-disjoint coverage, which is the case for running two.

**Agreement rate** — both-found over union, on accepted findings only. Low (<35%) means
genuine independence. High (>80%) means the second model is confirming rather than
searching. Neither is inherently good: high agreement on a *large* finding set is fine,
high agreement on a small one means one reviewer is coasting.

**False-positive rate** — rejected over proposed, per reviewer. The counterweight to unique
finds. A model with many unique finds and a 40% false-positive rate is generating noise the
adjudicator must absorb; watch the trend across runs, not one PR.

**Cite accuracy** — share of the reviewer's cites that survived independent verification.
Low cite accuracy is more damaging than a low finding count: it means the model's findings
cannot be trusted without full re-derivation, which erases the time saved.

**Severity over/under** — how often a reviewer rated a finding more (`+`) or less (`-`)
severe than the adjudicated result. A consistent skew is a calibration offset to correct for
when reading that model's raw output. On #4907, one model ran two notches *under* — it found
real blocking issues and proposed them as `major`.

**Check attribution** — which anti-bias check earned each finding. A check that produces
nothing on one PR is unremarkable; a check that produces nothing across many runs is either
dead weight or is being skipped, and `--summary` surfaces that.

**Search axis** — inward versus outward findings per reviewer. **A reviewer scoring zero on
an axis is the #4907 failure mode.** One model went 6-inward / 0-outward and the other
1-inward / 3-outward; each was blind where the other was strong, and neither knew it.

**File coverage** — changed files cited by neither reviewer. Docs and test files legitimately
appear here. A changed *source* file cited by neither is a coverage gap worth a direct look
before posting.

## Findings JSON schema

Written by the orchestrator after adjudication. Validation is strict — a bad enum fails
loudly rather than producing a wrong statistic.

```jsonc
{
  "pr": {
    "repo": "owner/repo",
    "number": 4907,
    "title": "...",
    "head_oid": "5cfc6566ed5c...",       // PR head reviewed; enables --prior on re-review
    "files": ["changed/file.py"]        // optional; enables the coverage section
  },
  "run": {
    "started_at": "2026-09-15T08:00:00Z",
    "effort": "high",
    "models": {"a": "claude-opus-5", "b": "gpt-5.6-sol", "adversary": "claude-opus-5"},
    "wall_clock_s": {"a": 420, "b": 380, "adversary": 140}
  },
  "verdict": "request_changes",          // request_changes|approve_with_conditions|approve|comment
  "findings": [
    {
      "id": "F1",                        // required
      "title": "...",                    // required
      "severity": "blocking",            // required: blocking|major|minor|question|nit
      "found_by": ["a"],                 // required: non-empty; "a"|"b"|"orchestrator"
      "status": "accepted",              // required: accepted|rejected|disputed
      "file": "app/x.py",
      "line": 500,
      "side": "RIGHT",                   // RIGHT (default) | LEFT, for inline anchoring
      "start_line": 495,                 // optional: multi-line inline comment
      "claim": "...",                    // one-paragraph body for the inline comment
      "suggestion": "    fixed = line()", // optional: emitted as a ```suggestion block
      "proposed_severity": {"a": "blocking"},
      "check_id": 1,                     // 1-8, or null
      "axis": "inward",                  // inward|outward
      "cite_ok": {"a": true},
      "reject_reason": null,
      "adversary": "upheld"              // upheld|rejected|downgraded|upgraded|null
    }
  ],
  "cleared": [
    {"claim": "...", "by": ["a"], "upheld": true}
  ],
  "coverage": {
    "files_cited": {"a": ["app/x.py"], "b": ["app/y.py"]}
  }
}
```

Fields consumed only when present: `pr.files`, `proposed_severity`, `check_id`, `axis`,
`cite_ok`, `adversary`, `cleared`, `coverage`, `run.wall_clock_s`. Omitting them drops the
corresponding section rather than failing — but each omission costs a diagnostic, so fill
them.

Note the `cleared` reshape: reviewers emit `{claim, how_verified}`, and the adjudicator
rewrites it as `{claim, by, upheld}` after merging duplicates across reviewers and — at
`xhigh` and above — re-testing each claim. An `upheld: false` entry means a risk a reviewer
dismissed was actually real; it should also appear in `findings` with
`found_by: ["orchestrator"]`.

## Ledger

One line of JSON per run, appended to `$XDG_STATE_HOME/copilot-skills/pr-review/ledger.jsonl`
(defaulting to `~/.local/state/copilot-skills/pr-review/ledger.jsonl`; override with
`PR_REVIEW_LEDGER`). It lives outside the skill directory because `package_skill.py` zips
everything there — a ledger inside the skill would ship your review history to anyone you
shared it with. It is also kept out of `~/.copilot/`, which is the CLI's own namespace, and
the `copilot-skills/` segment makes it obvious what wrote it. A ledger at either earlier
default (`~/.local/state/pr-review/`, `~/.copilot/pr-review/`) is moved on first run and
never overwrites an existing one.

```bash
python3 scripts/review_report.py --summary            # all runs
python3 scripts/review_report.py --summary --last 20  # recent trend
python3 scripts/review_report.py --prior 'owner/repo#123'   # last review of one PR
```

`--prior` reports the round number, the head SHA that was reviewed, and the prior verdict —
the inputs a re-review needs to scope itself to the delta. It only works if `pr.head_oid`
was set when the earlier round was recorded (take it from `PR_HEAD_OID` in `context.env`).

Per-model aggregates are keyed by **model name**, not reviewer slot, so swapping models mid
history still attributes correctly. The summary flags checks with zero findings once five or
more runs have accumulated.

Skip the ledger append with `--no-ledger` for test runs and re-reviews of the same PR, so
repeats do not inflate the aggregates.
